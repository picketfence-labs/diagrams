2026年10月25日更新｜Kong社内共有用

AIエージェントを業務に組み込むと、「誰がエージェントを使えるか」に加え、「エージェントが誰の権限で、どの接続先を使うか」が問題になる。Kong IdentityとToken Vaultは、この後者の資格情報管理をKong Gatewayの通信経路へ組み込むための選択肢である。

今回の調査から、まず次の4点を押さえたい。

  • 共有LLMキーの保管と入口認証は、既存のVault＋OIDC Plugin＋LLM Proxyが中心。 Token Vaultを必須にする要件ではない。
  • 利用者別のSaaS/MCP接続では、Token Vaultが価値を持つ。 OAuth同意、トークン保管、更新、接続先への提示を仲介し、接続先の資格情報をエージェントへ配る負担を減らせる。
  • 資格情報を保管することと、エージェントの行動を認可することは別。 利用者・エージェント・ツールの組合せ、実行内容、業務データへの権限は、Gatewayや接続先のポリシーと合わせて設計する。
  • 競合にも同種のbroker/proxyがある。 Kongの強み候補は、既存API/AI通信の制御と資格情報仲介を同じ経路に集約できる点にある。トークンをエージェントへ渡さない仕組み自体はKong独自ではない。

以下は公開仕様と社内の設計・Slack・Jiraを基にした機能比較。Kongは競合より内部情報まで読めているため、課題の見つかった件数で品質を比較していない。実機・性能・価格の比較は今回の対象外とした。実動作検証は利用者の指定により行わず、未実測の運用条件は資料評価の限界として記す。

1. Kongの各機能をどう使い分けるか

機能 主な役割 典型的な用途・位置付け
Vault Konnect Config Storeに保存したsecret、または外部Secrets Manager等のsecretを参照し、Gatewayが使う OpenAI等の共有APIキー、PAT、OAuth client secret、復号鍵。Konnect内で保管する構成も選べる。利用者のOAuth同意やRefresh Token更新を管理する機能とは別
OIDC Plugin 入口の認証、トークン検証、claimに基づく認可・マッピング Entra ID等のアクセストークンを検証。scope/group/role、Consumer/Group、Principal属性との連携。対応構成では外部ASへの交換も扱う
Kong Identity 主体情報と認証基盤を提供 Principals/Directoryで人やワークロードを表現。Auth Serverはトークン発行、Token Vaultは接続先資格情報の仲介を担当する
Token Vault 主体と接続先に対応する資格情報を管理・解決する 利用者ごとのGitHub/Slack等へのOAuth接続、保管・refresh、Gatewayへの資格情報提供。共有/static credential経路もある
LLM Proxy LLMへの通信を中継・制御する AI Proxy / AI Proxy Advanced等によるモデル振分け、provider認証、利用制御。共有keyならVaultと組み合わせる
MCP Proxy エージェントとMCP serverの通信を中継する AI MCP Proxy等によるtool公開・制御、外部MCP接続、Token Vaultの資格情報利用
A2A Proxy エージェント間の通信を中継する エージェント間の接続・入口制御。確認した開発版ではToken Vaultをauth providerに指定できない。多段委任は対応AS等の別構成

「LLM Proxy」「MCP Proxy」「A2A Proxy」は、本資料では通信経路の機能名として使用する。使えるplugin・runtime・設定は対象版に合わせて確認する。

Vaultの保管先にはKonnect Config Storeも選べるため、共有APIキー等をKonnect内に保存して利用できる。外部Secrets Managerを別途用意することは必須ではない。利用できる参照先のフィールドはbackendごとに異なる。Konnect Config Storeへの保存手順。

VaultとToken Vaultは併用もでき、例えばToken Vaultで扱う暗号鍵やstatic secretを既存Vaultの参照にする構成がある。Vaultの説明、OIDC Plugin、Vault reference連携の実装課題

Kong Identityの中でも役割は分かれる

論理機能 答える問い
Auth Server（AS） 誰に、どの用途のトークンを発行するか
Principals / Directory 検証したidentityが、どの主体record・属性に対応するか
Token Vault この主体がこの接続先を使うための資格情報は何か

ASは役割名であり、Kong Identity限定ではない。 Gateway入口のASにEntra IDやOktaを使える。接続先のOAuthトークンは、そのSaaS等が信頼するASが発行する。Kong Identityが任意のSaaSで通用するトークンを自由に作れるわけではない。

2. 代表的な3つのアプローチ

アプローチ 入口と出口で何をするか 向く要件
入口認証＋共有secret注入 OIDC等で呼出し元を認証し、Vaultから取得した共有keyを接続先へ付ける 複数LLMの共通利用、組織共通のAPIキー、PAT
Token Vaultによる資格情報仲介 入口の主体を確認し、その利用者・接続先に対応するOAuthトークン等を解決・注入する 社員別のGitHub/Slack等、複数SaaSの同意・更新をまとめる
Token Exchange / OBO / XAA等による委任 対応するASに対し、元の主体情報から別用途のトークン発行を要求する Entra OBO、企業IdPを跨ぐ委任、対応するagent間の委任

Token Vaultの内部要求にはToken Exchangeの形式を使う経路がある。ただし、保存済みトークンの再利用・refreshを含むbroker処理と、ASが新たな権限・用途のトークンを発行する処理は区別したい。「交換する」と聞いても、毎回新しいトークンになる、必ず権限が縮小される、任意のIdPで使える、とは限らない。 Token Vault紹介、RFC 8693、Kongの外部AS交換

2.1 共有LLMキー：OIDC＋Vault＋LLM Proxy

エージェントはGatewayへ提示するトークンAを持つ。Gatewayは呼出し元を認証し、利用可能なモデル等を判定する。LLM provider用のキーKはGateway側で付ける。

HTMLの図では、赤い認証経路が入口A、緑の経路が接続先K/B。Mermaid原稿では青・緑の背景で区別する。トークン名も矢印へ記載している。Vaultからの資格情報取得は概念表示であり、Konnect Config Storeの場合はKonnect側で参照を解決し、Gatewayへ設定を配信する。

Mermaid原稿を表示 
sequenceDiagram
    participant C as Client / Agent
    participant I as 入口IdP / AS（Entra等）
    participant G as Kong Gateway（OIDC + LLM Proxy）
    participant V as Vault（Konnect Config Store / 外部Secrets Manager等）
    participant L as LLM provider
    rect rgb(235, 244, 255)
        C->>I: OAuthで入口用トークンを取得
        I-->>C: A：Gateway向けアクセストークン
        C->>G: 推論リクエスト + A（Bearer）
        G->>G: OIDC/JWT検証、モデル許可・利用制御
    end
    rect rgb(235, 250, 238)
        G->>V: 設定したVault参照を解決
        V-->>G: K：provider用APIキー
        G->>L: 推論リクエスト + K（providerの認証方式）
        L-->>G: 推論結果
    end
    G-->>C: 推論結果

この用途ではToken Vaultは必須ではない。接続先が独自認証を要求しない自社APIで、Gatewayを必ず通る信頼境界を作れるなら、出口のOAuthトークンBも省ける。一方、外部LLM providerがAPIキーやIAM等を要求するなら、その資格情報の管理は残る。KongのSSO・モデル制御例

2.2 利用者別の外部MCP：Token Vault＋MCP Proxy

次は、利用者が接続先への同意・登録を済ませている通常実行の概念図。Kong Identity Auth Server、Principals、Token Vaultを別の論理機能として描いている。 Aの発行元は選択でき、この図の二つの取得経路は代替関係である。

Mermaid原稿を表示 
sequenceDiagram
    participant C as Client / Agent
    participant E as 外部IdP / AS（Entra等）
    participant G as Kong Gateway（OIDC + MCP Proxy）
    box Kong Identity
        participant K as Auth Server（選択時）
        participant P as Principals / Directory
        participant T as Token Vault
    end
    participant U as Upstream API / MCP
    rect rgb(235, 244, 255)
        alt 外部ASでAを取得する構成
            C->>E: OAuthによるトークン取得
            E-->>C: A：入口用アクセストークン
        else Kong Identity ASでAを取得する構成
            C->>K: 対応するOAuth grantによるトークン取得
            K-->>C: A：入口用アクセストークン
        end
        C->>G: MCPリクエスト + A（Bearer）
        G->>G: OIDC/JWT検証と入口・tool認可
        G->>T: Aと接続先を指定して資格情報を要求（mTLS）
        T->>T: trusted IdP・JWT署名等を検証
        T->>P: issuer / subjectから主体を解決（論理処理）
        P-->>T: Principal（構成によりUser JIT）
    end
    rect rgb(235, 250, 238)
        T-->>G: Bの保管値（token / 暗号化値 / 参照等）
        G->>G: 必要な復号・参照解決・更新処理
        G->>U: MCPリクエスト + B（OAuth Bearer等）
        U->>U: 接続先側でBを検証し、操作・データを認可
        U-->>G: 結果
    end
    G-->>C: 結果（Bはagentへ返さない）

ここで行われるのはAを手がかりに接続先用Bを解決する処理。Bは、事前のOAuth同意等で接続先ASが発行したものを使える。AとBの発行元・用途・権限は同一とは限らない。保存方式・refreshの担当は設計世代で異なるため、図は配置の理解を目的とする。社内MCP利用ガイド、Gateway側への処理移行

2.3 接続先OAuthの初回同意と更新は、別のフロー

利用者がまだ接続先を登録していなければ、ブラウザでその接続先の認証・同意が必要になる。下図はGatewayがcallback・code交換・更新を担当する構成の概念図である。10/24に取得したGateway開発ブランチでも該当処理を確認した。対象製品版への配備・顧客提供の確認とは分けて読む。

Mermaid原稿を表示 
sequenceDiagram
    actor U as 利用者 / Browser
    participant C as Agent
    participant G as Kong Gateway / 登録callback
    participant S as 接続先のOAuth AS
    participant T as Token Vault
    C->>G: 未登録の接続先を利用する
    G-->>C: 同意・登録への案内
    C-->>U: 登録URLを開く案内
    U->>G: 登録URLを開く
    G->>T: enrollmentをresolve（構成によりsubjectも送付）
    T->>T: subjectがあれば登録Principalと照合
    T-->>G: 接続先の認証URLとstate
    G-->>U: stateをbrowser cookieへ設定
    G-->>U: 接続先OAuthへredirect
    U->>S: 接続先へログイン・OAuth同意
    S-->>U: 認可code付きredirect
    U->>G: callbackへ認可codeを届ける
    G->>G: stateとbrowser cookieの一致を確認
    G->>T: resolve-stateで交換情報を取得
    T-->>G: token endpoint / client情報 / 適用時PKCE verifier
    rect rgb(235, 250, 238)
        G->>S: codeを交換（OAuth Authorization Code、PKCE等）
        S-->>G: B：Access Token、R：Refresh Token（発行される場合）
        G->>G: B / RをGatewayの鍵で暗号化
        G->>T: 暗号化credentialをcompleteで保管
    end
    Note over G,T: Identityは暗号化値を保存、Gatewayが復号する
    opt Bの更新が必要で、refresh可能な接続先
        T-->>G: 保存した資格情報を提供
        G->>S: Rを使ったOAuth refresh
        S-->>G: 更新したB、必要なら更新したR
        G->>T: 更新値を暗号化して書戻す
    end

実際にはcallbackと開始した利用者の結付け、接続先account、scope、期限切れ・失効、同時refreshを扱う必要がある。PAT/APIキーはこのOAuth refreshとは別の運用になる。設計資料はStorage Requirements、変更の追跡はAG-1735を参照。

登録した人との照合には構成条件がある。 確認したIdentity実装では、resolveへsubject tokenを提示した場合にPrincipalを照合し、省略した場合はその検査を行わない。単回URLやOAuth stateがあることだけで、人間の同一性まで保証されるとは見ない。登録入口を認証で保護し、subjectを渡す設計を確認する。主体照合を追加したPR1470

Gateway側では、共通の/_vault/callback[/initiate]を扱うpluginを追加したPR23103がmerge済み。/_vaultをOIDCで保護すると、initiateがそのリクエストのBearerをIdentityへ渡す。subjectをURLへ付けるだけでは本人確認にならない。code callbackはstateとbrowser cookieを照合する。関連PR23195単独は未mergeで、統合先PRとコードで確認している。

保存先と鍵を持つ場所は異なる。 今回のGateway実装では永続保存先はKonnect、復号・code交換・refreshはGateway側。Redisは任意の暗号化共有キャッシュであり、永続保存先の選択肢ではない。鍵の安全な投入・rotationとcache失効も運用設計に含める。shared OAuth資格情報の更新先をcredential_idで特定するPR22989も10/24にmergeされている。これらは開発コードの確認であり、全providerや複数DPでの動作保証ではない。

接続ごとのプロトコル・仕様

接続 認証・認可のプロトコル／仕様 読み分け
Agent ↔ 入口AS OAuth 2.0の対応grant。無人はClient Credentials、利用者の対話認証はAuthorization Code＋PKCE等。OIDCはログインidentityの層 Aの発行元は外部IdP/ASまたはKI AS。AgentのCCだけでは背後の利用者を認証できない
Agent → Gateway HTTPS＋OAuth Bearer（RFC 6750）。GatewayでJWT/JWKSやintrospection等による検証 Aのaudience・scope等を入口で評価する
Gateway → Token Vault mTLSによるGateway認証＋RFC 8693 grant形式の要求 subject token Aを提示しBを解決。provider/resource等の内部契約はKong固有で、汎用RFC完全準拠とは分ける
Token Vault → Principals Identity内の主体解決という論理処理 図は独立したOAuth通信が必ず発生することを意味しない
Gateway ↔ 接続先AS HTTPS＋OAuth Authorization Code（RFC 6749）、構成に応じPKCE（RFC 7636）、Refresh Token grant codeからB/Rを取得し、RからBを更新する。接続先ASが発行主体
Gateway → Upstream HTTPS／MCP＋OAuth Bearer、またはAPI key/PAT等の接続先固有方式 外部SaaSはBやKを受けて検証する。Gatewayが認証を終端する自社backendではBを省ける構成もある

内部の暗号化保管・credential管理APIはKong固有。公開鍵envelopeを採用することと、OAuthのトークン発行・交換に準拠することは別の評価軸になる。

3. 利用者とエージェントは、別に考える

20エージェントを1,000人が使う場合、Agent 7がClient Credentials grantで得たapp-onlyトークンだけでは、「今操作しているのは誰か」は分からない。利用者単位で制御するには、利用者を表す検証済みの文脈が必要になる。その上で、誰が、どのagentを通じて、どのtoolを使うかを結び付ける。

Kongの確認したTV経路は、トークンのissuer/subjectからPrincipalを解決する。構成によってUser JITによる自動作成もあるため、全員を事前に手動登録するという意味ではない。また、OAuth client登録、Principal、接続先credentialは別のrecordである。20＋1,000＝1,020という数は、各人・各agentを一つずつPrincipal化する場合の概算に留まる。Principal JITの社内議論

10/24に確認したIdentity mainには、trusted IdPのJIT・メールmappingに基づき、別のOIDC identityを既存user Principalへ対応付ける処理もある。単純にapp数を掛けた件数が必須とは言えず、mappingと本人性の設計を確認する。コードへのmergeと、顧客環境への提供は区別する。対応付けと同時JITの競合対策を追加したPR1510

OIDC Pluginには、claimに基づく認可、PrincipalのConsumer/Groupへのマッピング、属性を使う制御の入口がある。ただし、その属性を持つだけで接続先OAuth scopeが自動変換されたり、エージェントの全操作が安全になったりするわけではない。OIDC設定

TV内部にも、Principalのmetadataやgroupに応じて共有資格情報を選ぶselectorがある。たとえば部署ごとのAPIキーを選べるが、toolの引数や業務操作を認可するGateway/業務側のpolicyとは分ける。確認したIdentityコード

利用者全員にConsumerも複製する必要はない。 Principalの属性から既存Consumer Groupへ対応付け、OIDC＋ACLで「この部署の利用者にこの経路を許可する」といった制御を組める。Consumer単位のpluginが必要な時にConsumerへ対応させる。公開defaultはdirectoryあたり10万Principalだが、認証/lookupの100件/秒（cache hitを除く）や、1 Principalの10 identitiesは別の制約である。人数・identity数・cache miss時の負荷を分けて設計する。Principalの対応付け・公開上限、ACLによる認可

ただし、属性やGroupの取得自体は許可判断ではない。Groupの併合とcacheがあるため、userとagentの権限が自動で最小化されたり、部署変更や権限削除が即時に全経路へ反映されたりするとは限らない。これはToken Vaultによる接続先資格情報の選択とも別の制御である。確認したOIDC・Principal cacheの実装

追加取得した設計資料から分かったこと

設計資料では、直接エージェントとして認証する段階と、利用者＋エージェントを同時に識別して認可する段階が分かれている。初期TVは入口OIDCに限定し、Virtual Key、複数主体の認可、ID-JAGは段階的に追加する計画である。設計上の目標を、現在使える機能として一括して提案しない。

Kong Identityを入口ASにする追加設計では、利用者は企業SSOでログインし、KIがGateway用tokenを発行する。この構成は、企業IdPとclientの間を補う一方で、KI側の同意・Refresh Token・退職者処理を管理する必要がある。初期案は企業IdPでの停止をKI Refresh Tokenへ自動反映しないと明記している。接続先用token Bの更新とは別の注意点になる。

資料にはPrincipal JITの可否やIdP構成について相反する記述もある。計画機能は(未)付きで評価し、即時停止・GAの保証とは分けて実装と提供版を確認する。今回の追加ファイルは下記3原典の取得依頼に対して提供されたexportであり、各ファイルとGoogle ID・オンライン版の個別対応は未照合。Updated PRDへの入口、関連PRD 1、関連PRD 2

追加資料で変わった理解：リリース順と機能の境界

Token Vaultの中心である「接続先credentialを管理し、Gatewayが利用する」という理解は変わらない。追加資料で、提供順序に加え、別機能との責任分担と運用条件が明確になった。

7. 標準仕様との関係をどう捉えるか

OAuth/OIDCは入口認証や接続先への認可を支える。一方、credentialをどこに保管し、どのproxyが使い、どの管理画面で制御するかには各社固有の仕組みがある。独自の管理APIがあること自体はOAuth違反ではない。

対象 標準を使う部分と、製品固有の部分
Kong OIDC/OAuth、外部ASへの交換を利用。TVも標準grantの形式を使うが、取得コードのprovider/resource指定には固有の契約があり、汎用RFC対応ASへそのまま置換できるとは見ない
Palo Alto Code＋PKCE、JWT/JWKS、introspection等を説明。org/workspace、Idira/CIE、独自のidentity forwardingが加わる。標準Token Exchange/ID-JAGの具体的な交換profileは今回未確認
AWS RFC 8693 / JWT-bearer、Microsoft OBO等を説明。WAT、IAM/SigV4、KMS、Cedarとの組合せはAWSの運用モデル
Okta RFC 8693→ID-JAG→JWT-bearerとA2A委任の具体例がある。ID-JAG等のdraft、agent/resource/delegation links、STS/OPAの固有契約も含む

標準準拠の暫定ランクは、用途の学校式成績とは別の資料評価。B+は交換の具体的契約が比較的明確、Bは標準に基づく認証・接続を確認、Cは読めたprofileに具体的な規範差や未解決の境界、Uは対象の公開根拠が不足。Uを機能なしFとは扱わない。独立した適合認定によるAは今回付けていない。

対象 OAuth/OIDC基盤 交換・委任profile
Kong B+ TVはC（取得snapshotのresource指定等）。別のOIDC/MCP交換はB+
Palo Alto / Portkey B U（RFC 8693 / ID-JAGの具体的profile）
AWS AgentCore B+ B+（RFC 8693 / JWT-bearer OBO）

独自の保存・管理APIがあること自体はOAuth違反ではない。Kong TVのCをKong全体へ広げず、ID-JAG等のdraftと正式RFCも区別する。これらは実動作・相互運用試験の結果ではない。

標準方式の企業間委任に対応するclient・IdP・接続先が揃えば、個別SaaSのtoken保管を減らす選択肢もある。その場合はToken Vaultを経由しない構成も比較する。MCP Enterprise-Managed Authorization、社内PRDの参照入口

8. 実際の提案でどう選ぶか

まず聞きたい要件 有力な比較対象
「LLMの共有keyを配らず、使えるモデル・予算を制御したい」 Kong OIDC＋Vault＋LLM Proxy、Portkey/Prisma LLM Gateway、AWS Inference
「社員ごとのSaaS/MCPへの同意とrefreshをアプリから外したい」 Kong TV＋MCP Proxy、Portkey MCP Gateway、AWS Identity＋Gateway、Okta STS＋Agent Gateway
「既存KongのAPI/AI通信管理へ組み込みたい」 Kongの既存plugin・Vaultで足りる範囲を確認し、利用者別資格情報が必要な部分へTVを追加
「IdP中心にagent identityと委任を統一したい」 OktaのXAA/A2A、Palo AIS、AWS workload identity。Kongも入口認可・Principal・対応ASを含めた構成で比較
「AWS内のtool実行をIAMと引数policyで制御したい」 AgentCore Identity＋Gateway＋Policy
「Prismaのruntime securityとMCPの主体監査を揃えたい」 Portkey/Prisma＋AIS。region、tenant、対象agentとlicense条件を先に確認

Kong Token Vaultは、既存Kong経路で複数SaaSの利用者別資格情報を仲介する用途で検討価値が高い。共有secretだけなら既存Vault、企業内の委任ならIdP/ASのOBOや交換、agent行動の制御ならGateway/Policyまで含めて選ぶ。各機能の境界を揃えることで、Token Vault単体と競合の製品群全体を比べる偏りを避けられる。

導入判断前には、対象版での提供・有効化、user/agent/accountの結付け、失効の反映時間、refresh競合・鍵管理、監査の追跡範囲を確認する。KongのJiraには関連する失効通知、refresh/delete競合、QAと訂正の記録がある。これらは調査時点の開発・試験記録で、現行本番の未修正不具合を認定したものではない。

QAの指摘には後続修正がある。401/502のエラー分類は修正PR23664でマージされ、拒否時に接続先を呼ばないテストも追加された。一方、広いE2EテストとKonnect設定変換の再実装は調査時点でdraft。古い失敗を現行の未修正件数に数えることも、マージ済みコードを顧客利用可能と読み替えることもしない。複数DPでのcache共有・登録通知の試験と、全DPの失効時間・refresh競合・鍵更新の保証も別である。

監査は、資格情報の提供・更新・解除・登録を追跡する実装まで確認できた。主体・credential・traceの対応付けは強みになる一方、確認した配信はbest-effortで、欠落ゼロの保証ではない。また、資格情報の監査だけで「どの利用者が、どのagentを使い、どのtoolを実行したか」が全件つながるわけではない。Gatewayや業務側のログとの突合が必要になる。監査発行の実装、配送先対応

無効化も即時反映と決めつけない。AUでの負例報告に対する後続テスト変更は、無効化が反映されるまでpollingするものだった。別環境の成功は確認できたが、AU本番の再受入・全DPの失効時間は未確認である。

10/25の追加確認：JITと鍵管理

利用者JITとAgent JITは別。 ID-JAGの利用者PrincipalはTrusted IdPの設定により初回交換時に作成できる。対応チケットにはdevでの確認記録もある。一方、chained AgentのJITは別の未確定項目で、固定コードが出力するactorもOAuth client ID。任意のAgent実行instanceや多段委任を自動的に認証する意味ではない。利用者JIT、Agent JIT、固定実装

Citadelの公開鍵方式とversioned鍵設定は両立する。 前回、両者を広く設計差として扱った説明を修正する。Gatewayのstorage.keysはRSA/EC秘密鍵で、資格情報をAES-GCM＋公開鍵によるenvelopeへ封入する。管理者登録static secretはKI側が平文を受けて同じ形式に暗号化し、GatewayがOAuthで取得する資格情報はDP側で暗号化する。保管場所だけでなく、どの段階で平文を扱うかを選定時に確認する。鍵移行・旧鍵廃止の全運用や顧客提供は別の確認条件。Gateway暗号処理、static secretの封入
